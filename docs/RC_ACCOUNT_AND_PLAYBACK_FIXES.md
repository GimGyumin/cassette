# RC 계정 격리·삭제 복구·재생 준비 수정 — 2026-10-13

보고 환경: iPhone 16 Pro / iOS 27 / Navidrome. 셀룰러와 Wi-Fi 모두에서 곡 선택과 다음 곡 전환이 느리다는 보고를 기준으로 수정했다. 기존 작업 트리의 변경은 보존했으며, 이번 작업의 시작 상태는 `.derivedData-20261013-fix/baseline/`에 따로 보관했다.

## 결함 수정

| 경로 | 수정된 동작 |
| --- | --- |
| 연속 곡 삭제와 첫 요청 실패 | 편집 요청을 순서대로 처리한다. 행의 임시 위치 대신 각 곡 **출현의 UUID**를 보존하고, 실패 복구 후 다음 요청의 서버 인덱스를 다시 계산한다. 중복 곡도 구분한다. |
| 재생목록의 다운로드 삭제 | 개별 음원을 먼저 지우던 루프를 제거했다. DownloadService의 목록·앨범 참조 확인을 거쳐 공유 파일은 유지하고 해당 목록만 소유하는 파일을 지운다. |
| 삭제 응답 대기 중 계정 전환 | 요청 시작 계정의 ID와 세대 번호를 보존한다. 뒤늦은 응답은 다른 계정의 파일이나 커버를 삭제할 수 없다. |
| 재생목록 생성·설명 후속 요청 | 시작 시 받은 같은 SwiftSonic 클라이언트를 사용하고 각 응답 이후 계정 세대를 확인한다. 이전 계정의 결과로 새 계정에 후속 요청을 보내지 않는다. |
| 스트림 URL과 헤더의 계정 혼합 | 클라이언트와 자격 정보를 함께 준비하고 동일한 계정 세대인지 검사한다. 서버 클라이언트의 캐시와 생성 중인 작업도 계정 세대로 구분했다. |
| 로그아웃 뒤 즐겨찾기 재등장 | 롤백과 서버 동기화의 저장은 MainActor의 짧은 동기 작업 안에서 계정 검증과 함께 수행한다. 로그아웃 정리와 저장 사이에 실행이 교차할 수 없다. 같은 계정에서의 정상 실패 복구는 유지한다. |
| 삭제보다 늦은 목록 읽기 | 읽기 시작 시 내용 버전을 기록한다. 편집·삭제가 완료된 뒤 도착한 이전 읽기 결과는 캐시에 저장하지 않는다. |

계정 식별에는 `ServerState.accountRevision`도 포함한다. 따라서 A → B → A로 돌아와도 이전 A 세션의 요청이 다시 유효해지지 않는다. 재생목록 메타데이터 변경의 실패 롤백도 계정과 내용 버전을 확인한다.

## 재생 준비와 불필요한 작업

- 실제 재생 시작 확인 이벤트에서 다음 곡 준비를 요청한다. 기존의 최대 2초 간격 재생 시작 확인 루프를 제거했다.
- 진행률 처리에서도 잠금 화면 정보·스크로블·다운로드 작업보다 먼저 다음 곡 준비를 요청한다. 갭리스 전환 뒤의 메타데이터 작업도 준비를 먼저 요청한다.
- AVPlayer의 유한한 원격 progressive 음원은 실제 재생 가능한 버퍼가 1초(일반 네트워크) 또는 2초(제한된 네트워크) 이상이면 초기 처리량 추정 대기를 **한 번만** 단축한다. 탐색 중, 사용자 일시 정지, 로컬 파일, HLS·라디오는 이 경로를 사용하지 않는다. 복구 경로의 기본값은 보수적인 2초다.
- 정상적인 재생 중 끊김 복구에는 `automaticallyWaitsToMinimizeStalling = true`를 유지한다. 10초/20초의 재생 중 버퍼 목표도 유지한다. 초기 버퍼 관찰은 재생이 시작되면 해제한다.
- 갭리스가 다음 곡을 준비한 경우 크로스페이드용 별도 파일 사전 다운로드를 취소하고 새 요청도 막는다. 온도·메모리 예산 정책은 계속 적용된다. 오디오 분석 믹스를 갭리스 큐에 넣지 않던 기존 보호도 유지한다.

위 버퍼 수치는 음원 데이터의 재생 시간이며, 사용자가 곡을 누른 뒤 기다리는 실제 시간과 다르다. 서버 인코더가 첫 바이트를 늦게 보내는 경우까지 제거한다고 주장하지 않는다. [Apple의 자동 대기 설명](https://developer.apple.com/documentation/avfoundation/avplayer/automaticallywaitstominimizestalling), [즉시 재생 API](https://developer.apple.com/documentation/avfoundation/avplayer/playimmediately(atrate:)), [버퍼 목표 설명](https://developer.apple.com/documentation/avfoundation/avplayeritem/preferredforwardbufferduration).

## 검증

새 회귀 테스트는 겹친 삭제·복구, 중복 출현의 이동, 목록·앨범 공유 파일, 계정 전환 및 A → B → A, 늦은 읽기, 생성 후속 요청, URL·헤더 일치, 실제 ServerService의 계정별 생성 작업, 로그아웃 뒤 롤백, 재생 확인 직후 사전 준비, 중복 전송 방지를 검사한다. 실제 loopback HTTP 서버의 AAC·MP3 응답으로 재생과 EOF 전 다음 곡 요청을 검증한다.

기존 테스트 두 곳의 임의 서버 ID는 실제 활성 서버 ID로 바로잡았다. 활성 계정 확인을 느슨하게 하지 않았다.

최종 검증 결과:

- macOS 전체 **1,056개 테스트 / 184개 스위트 통과**. 테스트 실행 시간 69.398초.
- 계정·버퍼·HTTP·ServerService의 선택 실행 **31개 테스트 / 4개 스위트 통과**. 이후 전체 실행에서도 모두 통과했다.
- 준비된 로컬 음원의 전환 시 미디어 시계 손실: native 약 **0.029ms**, AudioStreaming 약 **−5.5ms**. 음수는 표본 추출 오차이며, 두 경로 모두 기존 **80ms 미만** 기준을 통과했다. 실제 서버 음원의 지연 감소 수치는 아니다.
- AAC·MP3 loopback HTTP 테스트는 작은 완전한 응답의 2초 이내 재생 시작, EOF 전 다음 곡 요청, 실제 다음 항목 전환, 헤더 보존을 확인했다.
- iOS 앱·UI 테스트 대상의 **arm64 / x86_64 빌드 성공**. 시뮬레이터 생성·UI 실행은 하지 않았다. UI 테스트 대상의 AppIntents 메타데이터 추출 생략 경고 1건이 있었고, 컴파일 오류는 없었다.
- `git diff --check` 통과.

## 실측 범위

로컬 macOS 테스트와 iOS 컴파일은 iPhone 16 Pro 실기기 검증을 대신하지 않는다. 실제 Navidrome 서버에서의 1–3초 지연 변화, 배터리 소모, 발열은 아직 계측하지 않았다. 실기기 확인은 원본 FLAC과 AAC/MP3 변환 각각에 대해 곡 선택, 연속 전환, 잠금 화면, Wi-Fi·셀룰러, 저전력 모드를 포함해야 한다.
