# 코드 구조 및 재생 전력 점검

이번 점검은 현재 작업 트리의 정적 분석이다. 실기기 CPU/GPU/전력 계측은 하지
않았으며, 기존 7–10% 대비 27% 배터리 소모의 원인을 확정한 결과가 아니다.
미커밋 변경이 많아 특정 변경을 회귀 원인으로 지목하지 않았다.

## 반영한 변경

- `FullPlayerView`에서 곡 정보, 탐색 바/재생 버튼, 하단 도구/출력 기기/볼륨,
  배경을 `Views/Main/Player`의 독립 컴포넌트로 분리했다. 곡 정보와 재생
  컨트롤의 본문은 그대로 이동했으며 외부에서 쓰이는 타입만 접근 범위를 넓혔다.
- `LyricsViewModel`의 타이밍 존재 여부와 화자 구분은 문서/표시 행 교체 시에만
  계산한다. 매 틱마다 전체 타임스탬프 배열과 Set을 만들지 않는다.
- `LyricPlaybackTimeline`은 로드 시 공백 행을 걸러내고 숫자 타이밍만 보관한다.
  매 프레임 전체 가사 문자열을 trim하거나 활성 후보 배열을 여러 번 만드는
  작업을 없앴다. 기존 겹치는 보컬, 동시 시작 우선순위, 다음 줄 선택, 역방향
  탐색 동작은 유지한다. 계산 복잡도는 여전히 O(행 수)이며 이진 탐색은 아니다.
- 가사 추적 Task가 sleep 중 뷰 모델을 강하게 유지하지 않도록 했고, 사용하지
  않는 Timer 저장 프로퍼티를 제거했다. 30/60 Hz 갱신 간격은 유지한다.
- 배경 비트 구독의 지연 작업을 SwiftUI `.task` 수명에 묶었다. 화면을 닫은
  뒤 취소되지 않은 별도 Task가 다시 구독하는 경로를 제거했다.
- 배경/이퀄라이저는 비활성 scene, 모션 줄이기, 저전력, 기존 비트 효과 중지
  설정을 반영한다. 메쉬 배경도 저전력 모드 전환과 `animated` 변경을 감지해
  애니메이션을 정지한다.

## 변경하지 않은 부분과 후속 점검 우선순위

1. **재생 엔진** — `PlayerService`는 약 3,700줄이다. 엔진 전환/중단 복구/seek/
   crossfade가 상태를 공유하므로 이번 UI 분리와 함께 대규모 재작성하지 않았다.
   별도 작업에서는 재생 상태 전이 테스트를 확보한 뒤 엔진 어댑터와 정책을 분리한다.
2. **비트 분석** — 현재 `CassettePerformance.forceBeatVisualsOff`가 이미 `true`다.
   따라서 비트 분석이 이번 배터리 증가의 원인이라고 단정할 수 없다. 이번 작업에서
   이 스위치를 바꾸거나 다른 기능을 추가로 끄지 않았다.
3. **커버 준비** — 최초 준비는 전체 앨범의 고해상도 커버 다운로드/색상 추출을
   수행한다. `downloadAllCovers`에는 진행 중 작업을 120ms마다 기다리는 polling도
   남아 있다. 준비 중/완료 후를 구분해 전력과 네트워크를 측정해야 한다.
4. **오디오와 다운로드 경쟁** — 재생 진행 확인, 자동 다운로드, 프리페치 경로를
   확인했지만 버퍼 안전 조건과 음질 설정은 바꾸지 않았다. 1 Mbps에서의 버퍼
   안정성은 실측 없이는 보장할 수 없다.
5. **큰 화면들** — `LyricsViewModel`, 앨범/플레이리스트 상세, 설정 화면은 여전히
   크다. 번역·가사 추적·저장소 정책 등 책임별 분리는 별도 회귀 테스트와 함께 진행한다.

## 검증

- 앱 및 테스트 Swift 파일에 대해 `swiftc -frontend -parse` 실행.
- 별도 Swift 실행 파일로 **실제 `LyricPlaybackTimeline` 구현**과 변경 전
  `activeRows` 알고리즘을 36,864개 입력 조합에서 비교해 동일 결과 확인.
  이 검증은 최소 표시 행 모형을 사용한 알고리즘 검사로, 앱 모듈 빌드는 아니다.
- 문서 교체에 따른 캐시 무효화 및 겹치는 보컬/공백/역방향 탐색의 회귀 테스트 추가.
  앱 XCTest/Swift Testing 전체 실행은 하지 않았다.
- 변경 대상 diff의 공백 오류 검사.
- 전체 Xcode 빌드, 실제 화면 비교, Instruments Energy/Time Profiler 측정은 미실행.
  문법 검사는 SwiftUI 타입 검사 및 actor isolation 검증을 대체하지 않는다.

## 실기기 비교 절차

같은 기기·빌드 구성·밝기·음량·출력 장치·재생 목록·음질·네트워크로 비교한다.
기기 온도와 시작 배터리 상태를 맞추고 초기 커버 준비 작업은 완료한 뒤 시작한다.

1. 로컬 다운로드곡: 화면 잠금 / 일반 재생 화면 / 가사 화면을 각각 같은 시간 재생.
2. CPU 호출 스택, GPU 작업, wakeup, 네트워크 전송량과 발열을 수집.
3. 가사 화면 반복 진입/이탈, 재생·일시 정지, 앱 전환, 저전력/모션 줄이기 전환 확인.
4. 온라인 재생은 Wi-Fi와 1 Mbps 제한을 분리해 버퍼 길이·언더런·현재 위치를 기록.
5. 자동 다운로드 허용/비허용을 각각 측정하되 음질을 동일하게 유지.

배터리 % 한 값만으로 개선을 판정하지 않는다. 같은 조건의 반복 측정과 호출
스택으로 원인을 확인한 뒤 재생 엔진 및 네트워크 정책 변경 범위를 정한다.

## 2026-09 후속 정리 (빌드·CI·저장소 위생)

위 점검에서 "후속"으로 남긴 항목 중 이번에 처리한 것과, 처리하지 않은 것의
근거를 기록한다.

### 처리한 항목

- **macOS 타깃 컴파일 복구** — `FullPlayerView.showLyricsChromeTemporarily()`가
  `#if os(iOS)` 블록 안에 있으면서 iOS/macOS 공통 코드에서 호출되고 있었다.
  함수 본문은 플랫폼 의존이 없으므로 가드 밖으로 옮겼다. macOS 빌드는
  `CODE_SIGNING_ALLOWED=NO`로 CI에서 다시 게이트된다.
- **경고 0건** — 이전 빌드에 있던 Swift 6 마이그레이션 경고(순수 데이터 타입의
  `MainActor` 기본 격리, 정적 상수 접근, Siri 헬퍼 격리)를 실제 수정으로 제거했다.
  `MediaSessionRepresentable` 적합성 경고만 남으며, 프레임워크가 격리를 명시하지
  않은 데서 오는 항목이라 `CONTRIBUTING.md`의 "Known acceptable warnings"에
  근거·재검토 조건과 함께 등록하고 CI 필터에 반영했다.
- **CI 추가** — `.github/workflows/ci.yml`: iOS 빌드(경고 게이트), macOS 빌드
  (경고 게이트), 단위 테스트(macOS destination). 이전에는 릴리스 태그에서만
  테스트가 돌아 PR 단계 게이트가 없었다.
- **저장소 위생** — 추적 중이던 빌드 산출물(`.derivedData*` 하위 8경로)과
  `.DS_Store` 8개를 인덱스에서 제거하고 `.gitignore`에 `.derivedData*/`,
  `*.xcresult`, `.DS_Store`, `*.zip`, `.cursor-tmp/`를 추가했다.
  `Cassette/Localizable.xcstrings`는 추적 대상이 아니어서 새로 클론하면 번역이
  전부 사라지던 문제를 수정해 추적에 포함했다. 타깃에서 제외돼 있던
  `Cassette/Settings.bundle`(9파일)은 인앱 설정과 중복·불일치 상태였으므로 삭제했다.
- **테스트 보강** — 품질 라벨 분류기(돌비 코덱·채널 레이아웃·JOC·배지 우선순위·
  게이팅)와 `CacheFormat`(선택 가능 목록·Subsonic 매핑·레거시 마이그레이션)에
  회귀 테스트 13개를 추가했다. 총 687개 `@Test` / 76파일, macOS 목적지에서 746개
  테스트 케이스가 전부 통과한다.
- **테스트 타깃 복구** — 조사 중 테스트 타깃이 macOS 목적지에서 **컴파일조차 되지
  않는 상태**임을 확인했다(`LibraryServiceProtocol.song(id:)` 요구사항 추가로 8개
  스텁이 미적합, iOS 27 가용성 애노테이션이 붙은 Swift Testing `@Suite`/`@Test`,
  `Foundation` 미임포트로 `UUID` 미해결). 세 원인을 모두 수정했다. 이 상태에서는
  새로 추가한 CI의 단위 테스트 잡이 즉시 실패했을 것이므로, CI 추가와 함께 반드시
  필요한 수정이었다.
- **실행 결과 드러난 기존 실패 5건 정리** — 컴파일이 되게 만든 뒤 실제로 돌려보니
  5건이 실패했다. 원인별로 나눠 처리했다.
  - 아트워크 로더 **실제 버그**(프로덕션 수정): 실패 백오프가 URL만을 키로 삼아,
    자격증명 없이 한 번 실패한 커버 URL은 쿨다운 동안 인증된 재시도까지 막혔다
    (Cloudflare 보호 서버에서 잠금화면 아트워크 누락). 백오프 키를 URL + 자격증명
    서명으로 바꿨다.
  - 낡은 테스트 기대값 2건: `SettingsIcon` 기본 처리가 subdued(28pt)로 바뀐 뒤
    기대값이 30pt로 남아 있었고, URLSession이 URLProtocol에 요청 본문을
    `httpBodyStream`으로 넘기는 경우를 테스트가 고려하지 않았다. 테스트를 현재
    계약에 맞게 수정하고 28pt 기본값 검증을 추가했다.
  - 새로 추가한 테스트 2건은 로케일/샌드박스 의존이었다: 채널 레이아웃 문자열은
    로케일에 따라 번역되고, 샌드박스 테스트 호스트에서는 임시 `UserDefaults`
    스위트가 앱 도메인을 물려받을 수 있다. 단언을 계약 기준으로 바꾸고,
    `CacheFormat`의 레거시 매핑은 순수 함수(`migratedRawValue`)로 분리해
    `UserDefaults` 없이 검증하도록 했다.
- **문서** — `docs/ARCHITECTURE.md` 신설(레이어·DI·재생 파이프라인·설정·플랫폼
  표면·테스트, 그리고 아래 재생 엔진 부채의 계획).

### 처리하지 않은 항목

1. **재생 엔진 분해** — 위에서 "테스트 확보 후 분리"라고 적은 항목이다. 이번에
   결합도를 계측했고, 기계적 분해가 안전하지 않다는 근거를 확보했다: 재생 경로가
   다른 섹션의 private 멤버 68개, 트랙 종료 경로가 58개, iOS 오디오 세션 블록이
   34개를 참조한다. 파일만 쪼개면 약 100개 멤버를 `internal`로 넓혀야 하고
   가독성만 나빠진다. `docs/ARCHITECTURE.md`에 상태 소유권 기준 분해 계획
   (`CrossfadeEngine`, `PlaybackSessionStore`, `NowPlayingPusher`,
   `AudioRouteCoordinator`)과 PR 단위 검증 항목을 기록했고, actor-private 상태에
   접근하지 않는 `AudioStreamingDelegate`만 먼저 분리했다.
2. **UI 테스트** — 여전히 셸 내비게이션 수준 2파일이다. 실기기 검증이 필요한
   영역(재생·합성·제스처)이라 시뮬레이터 기반 UI 테스트 확대는 별도 결정이 필요하다.
3. **배터리/전력 계측** — 위 절차대로 실기기 측정이 필요하며 정적 분석으로
   대체할 수 없다. 이번 작업은 빌드·CI·저장소 위생 범위다.
